# Plan: chunked attachment-content contract (`canto-data` v1.1.0)

**Status:** Draft — requires approval before implementation.

## Decision record

The requested release is a backwards-compatible **minor** release, as selected
for the new public data-model capability:

- Package: `canto-data` **v1.0.4 → v1.1.0**.
- Journal/export schema: **0.17.0 → 0.18.0**.
- Archive manifest format remains **version 1**.
- Existing attachment records and v1 `.canto.zip` archives remain readable
  without conversion.
- This package defines and validates attachment-content metadata only. It does
  not implement encryption, storage, chunk I/O, sync scheduling, or Google
  Drive.

An older `canto-data`/Canto consumer will correctly reject a future `0.18.0`
archive. “Backwards-compatible” here means that v1.1.0 can read all prior
schemas and that the new type preserves all existing required fields; it cannot
make an older consumer implement a new storage representation.

## Problem

Canto currently represents every attachment as one opaque, base64-encoded
value. The app must therefore read, decrypt, re-encrypt, encode, and upload an
entire large asset at once. The current base64 encoder alone raised RSS by about
1.6 GiB when given a 32 MiB input; two concurrent 80 MiB-video transfers can
therefore exhaust Android memory.

The long-term solution is chunked attachment content. This first milestone
creates the portable, validated content descriptor needed by later Canto
storage and sync adapters while keeping the existing attachment and archive
contracts usable.

## Scope

### In scope — this repository

- `Attachment` metadata contract and root exports.
- Runtime validation and type guards.
- Schema 0.18.0 migration-chain support.
- Archive-helper semantics for a chunked local attachment exported into the
  existing flat v1 ZIP representation.
- Tests, README, changelog, package/lock version, and release verification.

### Explicitly out of scope — follow-on Canto work

- Native filesystem, IndexedDB, and web blob storage implementations.
- AES-GCM framing, nonce/key/AAD derivation, encrypt/decrypt code, and
  integrity verification execution.
- Reading/writing/reassembling chunk bytes.
- Google Drive resumable uploads, remote chunk naming, retry/cancellation, and
  byte-budgeted scheduling.
- Automatic conversion of existing large monolithic local attachments. A later
  app plan must define a safe migration/fallback for those assets.

## Data contract

### 1. Preserve legacy `Attachment`

`Attachment.path` remains a required string and all current properties remain
unchanged. Existing records have no `content` property and continue to describe
legacy monolithic attachment bytes.

```ts
export interface Attachment {
  id: string;
  path: string;
  name: string;
  type: "image" | "file";
  encrypted: boolean;
  size?: number;
  deleted: boolean;
  content?: AttachmentContent;
}
```

`path` is an opaque locator owned by a Canto storage adapter. For a chunked
attachment it locates that adapter’s attachment root/manifest, not necessarily
a single byte-for-byte file. The old assumption that it names one file is only
valid when `content` is absent.

### 2. Add one small, extensible descriptor

```ts
export const CHUNKED_ATTACHMENT_CONTENT_FORMAT = "canto-chunked-v1" as const;

export interface ChunkedAttachmentContent {
  format: typeof CHUNKED_ATTACHMENT_CONTENT_FORMAT;
  /** Exact plaintext byte length. Authoritative when present. */
  byteLength: number;
  /** Maximum plaintext bytes in one chunk. */
  chunkSize: number;
  /** Number of ordered chunks. */
  chunkCount: number;
}

export type AttachmentContent = ChunkedAttachmentContent;
```

The discriminated `AttachmentContent` union is the seam for later formats.
Absence means legacy content; it is deliberately not represented by a second
variant. `Attachment.size` stays optional and historical/consumer-provided, so
it is not required to equal `content.byteLength`.

The descriptor does **not** include provider IDs, file paths, keys, nonces,
ciphertext, full-file hashes, or an array of chunk IDs. Storage/sync adapters
choose their own locations, while the future Canto protocol must derive chunk
identity deterministically from the journal, attachment ID, and zero-based
chunk index.

### 3. Normative descriptor invariants

`validateChunkedAttachmentContent` and `isChunkedAttachmentContent` must
require:

- `format === 'canto-chunked-v1'`;
- `byteLength`, `chunkSize`, and `chunkCount` are non-negative safe integers;
- `chunkSize > 0`;
- `chunkCount === Math.ceil(byteLength / chunkSize)` (therefore an empty
  attachment has `chunkCount: 0`);
- no application-specific minimum/maximum chunk size. That is a storage-adapter
  performance policy, not a portable data-model invariant.

`validateAttachment` calls the descriptor validator only when `content` is
present. Errors use the existing nested field-path convention, e.g.
`page.images[0].content.chunkCount`.

## Archive semantics

`.canto.zip` remains a portable, flat v1 format with one reconstructed raw
attachment at `attachments/{type}-{id}.{ext}`. It does not contain Canto local
or remote chunk frames.

1. `collectAttachmentEntries` keeps its current path-based uniqueness and
   returns an optional `content` descriptor on `AttachmentEntry` so a caller
   can select a chunk-aware reader without re-searching pages.
2. `rewriteAttachmentPaths` remains the archive-preparation helper. When it
   rewrites an attachment path through the provided ZIP path map, it must omit
   `content`: the mapped ZIP path identifies the reconstructed legacy payload,
   not a chunk-root.
3. A path not present in the map is unchanged, including its descriptor.
4. `serializePages`/`deserializePages` remain generic JSON helpers and preserve
   `content` when it is actually part of the provided page object.

This preserves existing archive import/export interoperability while making it
possible for the later Canto exporter to stream-reconstruct a chunked attachment
into one archive member. The subsequent importer can then choose the current
storage representation and add a descriptor only after successfully writing it.

## Implementation steps

### 1. Public types and exports

1. In `src/types.ts`, add `CHUNKED_ATTACHMENT_CONTENT_FORMAT`,
   `ChunkedAttachmentContent`, `AttachmentContent`, and optional
   `Attachment.content` exactly as above.
2. In `src/index.ts`, export the new constant and types from the root package.
3. Do not change existing `Attachment`, `Page`, archive-manifest, or package
   export paths beyond additive exports.

### 2. Validation interface

1. Add `isChunkedAttachmentContent` beside the existing attachment guard.
2. Add `validateChunkedAttachmentContent` beside the existing attachment
   validator, using the established `ValidationError` and field-path style.
3. Validate safe-integer/count arithmetic before computing the expected count
   so malformed numeric inputs cannot exploit floating-point coercion.
4. Integrate the optional validation into `isAttachment` and
   `validateAttachment`; legacy descriptors-absent values remain accepted.
5. Re-export both validation functions from `src/index.ts`.

### 3. Archive helper behavior

1. Extend `AttachmentEntry` in `src/format.ts` with
   `content?: AttachmentContent` and populate it from each source attachment.
2. Refactor the cloning inside `rewriteAttachmentPaths` into one local helper
   used by images and files. When a path maps to a ZIP filename, return an
   attachment clone with the ZIP path and without `content`; when it does not,
   preserve every existing property.
3. Preserve the current deleted filtering, empty-path skip, path dedupe,
   filename generation, and non-mutating behavior.
4. Document the flat-v1 canonicalization rule in the helper’s doc comment.

### 4. Schema and migration chain

1. Change `SCHEMA_VERSION` in `src/version.ts` to `0.18.0`.
2. Add and register `src/migrations/v0_17_0_to_v0_18_0.ts`.
3. Make that migration a no-op: legacy data must remain descriptor-absent and
   no byte/storage conversion belongs in this library.
4. Verify the full forward path remains contiguous:
   `0.16.0 → 0.17.0 → 0.18.0`.

### 5. Tests (100% coverage remains mandatory)

1. Extend `src/__tests__/validation.test.ts` with factories and direct guard /
   validator tests for valid legacy and valid chunked attachments.
2. Add one test per descriptor invariant: unknown format, non-object content,
   non-integer/unsafe/negative values, zero `chunkSize`, and each count/length
   mismatch. Assert exact field paths.
3. Add nested `Page.images` and `Page.files` validation cases to prove
   descriptor errors retain the full field path.
4. Update `src/__tests__/format.test.ts` to assert:
   - collection includes descriptor metadata in `AttachmentEntry`;
   - a mapped path has `content` removed by `rewriteAttachmentPaths`;
   - an unmapped path preserves it;
   - legacy path rewrite/dedupe/deleted/empty-path behavior is unchanged;
   - generic page serialization/deserialization round-trips the descriptor.
5. Update `src/__tests__/migration.test.ts` to assert the registered no-op
   `0.17.0 → 0.18.0` step, the full `0.16.0 → 0.18.0` chain, and unchanged
   descriptor-absent legacy data.
6. Update `src/__tests__/version.test.ts` / `format.test.ts` expectations for
   schema `0.18.0`, including `buildExportManifest`.

### 6. Documentation and release

1. Add a top `CHANGELOG.md` entry for **v1.1.0** explaining the additive
   descriptor, schema 0.18.0, no-op migration, archive-v1 behavior, and strict
   non-ownership of storage/crypto/sync.
2. Set `package.json` and root `package-lock.json` package versions to `1.1.0`.
   Normalize the lockfile’s currently stale root version while doing so.
3. Update README version/test badges, the attachment model tree, schema policy,
   migration history, current manifest example, and export-format section.
4. State clearly that old archives and descriptor-absent attachments are
   supported, while a 0.17 reader cannot consume a future 0.18 archive.
5. Do not claim that this package encrypts, stores, streams, or uploads bytes.

## Acceptance criteria

- `canto-data@1.1.0` exposes a small, discriminated chunked-content descriptor
  without weakening or removing any legacy `Attachment` field.
- Schema 0.18.0 reads 0.16/0.17 data through a complete forward migration path
  without inventing descriptors or converting bytes.
- Runtime guards and validators reject malformed descriptors with precise paths
  and continue accepting every valid legacy attachment.
- Flat v1 ZIP preparation removes the local chunk descriptor only when it
  rewrites to the reconstructed archive payload; generic JSON round trips
  preserve it.
- The package stays dependency-free and does not gain storage, cryptography,
  or remote-provider behavior.
- All coverage, build, repository verification, formatting, and package dry-run
  gates pass.

## Follow-on dependency: Canto app plan

Only after this package is released should Canto update its dependency and
implement the actual bounded-memory protocol: chunked local adapters on native
and web, per-chunk authenticated encryption, migration/fallback policy for
legacy large blobs, streaming/archive adapters, resumable Google Drive
transfers, byte-budgeted concurrency, cancellation, and device-level memory
profiling. That app work must not begin by changing this descriptor contract
without a new approved plan.
