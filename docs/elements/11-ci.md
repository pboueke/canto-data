# 11 — Continuous integration

## Why

CI must run the same gate as a fresh local checkout, on a clean machine, from
an identified revision. It must not be a differently-defined checklist, and PR
code must never run with release credentials.

## How to use

- `.github/workflows/ci.yml` runs on PRs and pushes to `main`:
  - installs rootless Podman,
  - prints the tested revision,
  - resolves the version comparison base from the event payload (PR base SHA,
    otherwise the push `before` SHA, otherwise `HEAD`),
  - runs the single `make verify` gate (which already includes the Node
    18/20/22/24 packaged-consumer legs and the Chromium leg),
  - uploads the machine-readable test/coverage reports as evidence named after
    the revision.
- Actions are pinned by commit SHA and checkouts use
  `persist-credentials: false`.
- `.github/workflows/release-tag.yml` is the tag-only helper:
  - on push to `main`, it re-runs the repository's own version check
    (`toolkit/tools/cli/run.js version-check --base HEAD`), so a tag cannot
    appear while the changelog, manifest, lockfile and README disagree;
  - it tags the pushed commit `v<version>` only when the tag is absent and
    `main` has not advanced past that push, and it never moves an existing
    tag;
  - it holds `contents: write` only for that tag push, uses a one-shot token
    URL instead of persisting credentials, and never publishes.

## Authority

The workflow owns when and where CI runs; the Makefile owns what a gate is.
There is no separate CI-only check definition. Repository settings (required
checks, branch protection) are owner-managed, not encoded here.

## How to replace

Change the runner or provider by porting the same steps: install the host
requirements, call `make verify`, upload evidence named for the revision, and
keep workflow permissions minimal and the tag helper tag-only.
